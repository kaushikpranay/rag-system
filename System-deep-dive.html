Deployment + data-flow topology: two Vercel-hosted React frontends talk over HTTPS to a single FastAPI backend on EC2 (behind nginx), which fans out to LangGraph/Groq for inference and to RDS/DynamoDB/SQS/S3 for storage.

Layer Technology Rationale
State Machine LangGraph Deterministic, debuggable control over agent flow via StateGraph.
LLM Groq (Llama-3.1) Sub-200ms latency for real-time responsiveness.
Embeddings AWS Bedrock Titan V2 Managed, cost-effective 1024-dim vector generation.
Vector DB RDS (pgvector) Unified relational + vector storage in a single AWS service.
Memory DynamoDB Sub-ms performance with auto-TTL for session cleanup.
Queue Amazon SQS Reliable decoupling for human escalation workflows.

The AgentState Schema

Every node in the graph communicates via a central state object:

class AgentState(TypedDict):
    query: str                    # User's question
    session_id: str               # UUID tracking
    chat_history: List[dict]      # Context from DynamoDB
    retrieved_chunks: List[dict]  # Vectors from pgvector
    answer: str                   # Final LLM response
    retry_count: int              # Attempt tracker (max 3)

3. Node-by-Node Deep Dive

Adaptive Retrieval

The Retrieval Strategy

We implement a progressive search widening strategy. If the LLM lacks confidence, we loop back and fetch more content with lower similarity requirements.

Attempt Similarity Threshold Top K
1 0.30 5
2 0.20 8
3 0.10 11
Evaluation

Low-Confidence Detection

Instead of relying on LLM-generated scores, we use a robust list of 17 refusal phrases to trigger the retry or escalation flow.

phrases = ["not enough information", "cannot answer", "no relevant context"]
refused = any(p in answer.lower() for p in phrases)

4. Vector Database — pgvector

-- Semantic Search Query
SELECT content, metadata, 1 - (embedding <=> %s::vector) AS similarity
FROM documents
WHERE 1 - (embedding <=> %s::vector) > 0.3
ORDER BY similarity DESC
LIMIT 5;

We leverage the <=> cosine distance operator in PostgreSQL to perform high-speed semantic matching directly alongside our relational metadata.

5. Cross-User Knowledge Sharing

Implemented in GET /queue-status/{session_id} (app/api/main.py). Every poll checks two tiers, in order:

  1. Session match: a row in documents tagged metadata->>'source' = 'human_verified' for this exact session_id and query.
  2. Cross-session fallback: if none, any row with the same query text (case-insensitive) verified for any other session — so once one user's escalation is resolved, every other user asking the same thing gets the answer instantly, no re-escalation needed.

6. Session Memory — DynamoDB

app/memory/dynamodb_client.py stores conversation history per session in a single table (rag-session-memory, keyed by session_id):

  • get_session reads the history list attribute (query/answer/timestamp entries).
  • save_session appends a new turn and rewrites the item with a 24-hour expires_at TTL, so DynamoDB auto-expires stale sessions.
  • Verified escalation answers are also written back here (prefixed [VERIFIED BY AGENT]) so the chat's memory reflects the human-approved answer.

7. Escalation Pipeline — SQS

app/escalation/sqs_worker.py wraps a single SQS queue with four operations: send_to_sqs (agent pushes a low-confidence query), receive_from_sqs (dashboard polls up to N messages), delete_from_sqs (message removed once an agent resolves it), and get_queue_depth (powers the dashboard's live queue counter).

Resolution (POST /dashboard/escalations/resolve) is a 3-way write: the verified answer goes into pgvector (store_verified_answer), archived to S3 (archive_verified_answer), and written into the session's DynamoDB history — then the SQS message is deleted.

8. Document Ingestion Pipeline

app/ingestion/pipeline.py is a standalone script (python -m app.ingestion.pipeline): it lists PDFs under the raw-documents/ prefix in S3, downloads each to a temp dir, parses it with PyPDFLoader, splits it with RecursiveCharacterTextSplitter (chunk size 1000, overlap 100), and embeds/stores the chunks via store_chunks into pgvector. This is how the base knowledge corpus gets seeded, independent of the human-verified answers written at runtime.

9. Security Hardening

  • Headers: SecurityHeadersMiddleware in main.py sets X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Strict-Transport-Security, a restrictive Content-Security-Policy, and Referrer-Policy: no-referrer on every response.
  • CORS: CORSMiddleware only allows the exact origins listed in the FRONTEND_ORIGINS env var (the two Vercel URLs in production) — anything else is rejected at preflight.
  • Rate limiting: slowapi caps /query at 20/min, /escalate at 5/min, dashboard /escalations at 30/min and /escalations/resolve at 10/min per client.
  • Input handling: app/utils/sanitizer.py strips/validates queries (sanitize_query), flags prompt-injection attempts before they reach the LLM (detect_prompt_injection), and masks PII in logs (mask_pii).
  • Dashboard auth: a single shared password hash (DASHBOARD_PASSWORD_HASH) checked via POST /dashboard/login, then required as a Bearer token on every other dashboard route.

10. CI/CD Pipeline

Backend: .github/workflows/ci.yml runs pytest on every push/PR. On success on main, cd.yml triggers, SSHs into the EC2 box, does git pull origin main, reinstalls requirements.txt, and restarts the service with supervisorctl restart fastapi — nginx in front handles TLS termination and reverse proxying to uvicorn on port 8000.

Frontends: frontend/chat and frontend/dashboard are each a separate Vercel project connected to the same GitHub repo — a push to main auto-triggers a Vercel build/deploy for both, independent of the backend's EC2 pipeline.

11. Frontend Polling

frontend/chat/src/hooks/usePolling.js polls GET /queue-status every 5 seconds (POLL_INTERVAL_MS) for each pending escalation, up to 60 attempts (MAX_POLLS — a 5-minute ceiling) before giving up and firing onTimeout. As soon as in_queue flips false with an answer, onResolved fires and the interval is cleared once every pending query is settled — no websockets needed for this polling cadence.

12. Interview Q&A — Deep Dive

Q: Why LangGraph instead of a simple LangChain agent?
LangChain agents are often unpredictable as they decide tool usage on the fly. LangGraph provides a deterministic state machine, allowing us to enforce specific retry logic, error handling, and manual escalation paths that are 100% reliable in a production customer care environment.
Q: How do you handle cross-user knowledge sharing?
When a human agent verifies an answer, we embed only the query and store it in RDS with a 'human_verified' tag. Every new user query first searches this high-priority verified pool before falling back to general documentation, ensuring accurate answers are reused across the entire user base.
Q: What is the average latency?
The typical end-to-end request takes between 350ms to 600ms. This includes DynamoDB history retrieval, Bedrock embedding generation, pgvector search, and Groq inference.
