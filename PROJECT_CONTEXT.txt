--- WHY BUILT ---
To demonstrate a production-ready, self-improving AI customer care system for interviews/resume.
Core challenge solved: LLMs hallucinate and can't answer domain-specific questions reliably.
Solution: RAG (retrieve real docs first) + human escalation loop + knowledge accumulation.
Key differentiator: Human-verified answers are stored as vectors and reused for ALL future users
automatically — system gets smarter over time without manual retraining.

--- WHAT IT DOES ---
1. User asks question via chat UI.
2. Agent retrieves relevant docs from vector DB (pgvector on RDS).
3. LLM (Llama 3.1 via Groq) generates answer using retrieved context + chat history.
4. If LLM is not confident → retries up to 3x with wider search params.
5. After 3 failed attempts → escalates to human agent via SQS queue.
6. Human agent answers via Streamlit dashboard → answer embedded and stored in vector DB.
7. Next user asking similar question gets the human-verified answer automatically.

--- TECH STACK ---
LLM: Groq API (llama-3.1-8b-instant) — sub-200ms inference
Embeddings: AWS Bedrock (amazon.titan-embed-text-v2:0) — 1024-dim vectors
State Machine: LangGraph (StateGraph) — deterministic multi-node agent
Vector DB: AWS RDS PostgreSQL + pgvector extension
Session Memory: AWS DynamoDB (TTL=24h per session)
Message Queue: AWS SQS (escalation workflow)
Document Storage: AWS S3 (raw PDFs in raw-documents/, verified answers in verified-answers/)
Backend: FastAPI + uvicorn (served via nginx + supervisor on EC2)
Chat UI: Vanilla HTML/JS (served by FastAPI at /)
Agent Dashboard: Streamlit (port 8501)
CI/CD: GitHub Actions → SSH → EC2 (appleboy/ssh-action)
Process Manager: supervisor (restarts fastapi + streamlit on crash)
Reverse Proxy: nginx
Security: slowapi (rate limiting), PII masking, prompt injection guard, CSP headers

--- AGENT STATE MACHINE (graph.py) ---
AgentState fields: query, session_id, chat_history, retrieved_chunks, context, answer,
                   confidence (high/low/retry), escalate (bool), retry_count (int), error

NODE FLOW:
input_node → [route_after_input] → session_node → retrieval_node → context_node
→ llm_node → evaluation_node → [route_after_evaluation] → output_node → END

RETRY LOOP: evaluation_node routes back to retrieval_node up to 2 more times (3 total).
Each retry widens search: top_k 5→8→11, min_similarity 0.30→0.20→0.10, human_threshold 0.55→0.50→0.45

NODE DETAILS:
- input_node: strips whitespace, sets error if empty
- session_node: loads last N turns from DynamoDB
- retrieval_node: 1st checks human_verified pool (semantic), then general docs
- context_node: skips rebuild if human-verified context already set
- llm_node: builds prompt with chat history + context, calls Groq
- evaluation_node: checks 16 refusal phrases → high/retry/low confidence
- output_node: if escalate → send_to_sqs + save escalation msg to DynamoDB
              if resolved → save good answer to DynamoDB

LLM PROMPT RULES:
- Use chat history for conversational context (follow-ups)
- Use retrieved context for factual answers
- If neither has answer → say "I don't have enough information to answer this."
- Never say "based on previous conversation" — answer naturally
- Only reference past conversation if user explicitly asks

--- RETRIEVAL LAYER (pgvector_client.py) ---
DB TABLE: documents(id SERIAL, content TEXT, metadata JSONB, embedding vector(1024))
Two search functions:
1. retrieve_similar(query, top_k, min_similarity) — general semantic search
   SQL: SELECT content, metadata, 1-(embedding<=>%s::vector) AS similarity
        FROM documents WHERE similarity > min_sim ORDER BY embedding<=>query LIMIT top_k
2. search_human_verified(query, top_k=3) — searches only WHERE metadata->>'source'='human_verified'
   Embeds only the query (not the answer) for matching — same as how it was stored

BEDROCK CLIENT: Single module-level boto3 client (not per-call) — performance optimization

--- MEMORY LAYER (dynamodb_client.py) ---
Table: rag-session-memory (partition key: session_id)
Schema: {session_id: str, history: [{query, answer, timestamp}], expires_at: TTL}
TTL: 24 hours from last write
get_session(session_id) → list of {query, answer, timestamp} dicts
save_session(session_id, query, answer) → appends to history list, rewrites item

--- ESCALATION PIPELINE ---
FLOW: LLM fails 3x → output_node → send_to_sqs(session_id, query, answer)
SQS message body: {session_id, query, answer}
Human agent: opens Streamlit dashboard → clicks "Fetch Escalated Queries" → reads SQS
→ types verified answer → clicks Submit:
  1. get_bedrock_embedding(query) [query only, not answer]
  2. INSERT into RDS: content="Q: {query}\nA: {answer}", metadata={source:"human_verified", query, session_id, verified_at}
  3. PUT to S3: verified-answers/{session_id}_{timestamp}.json
  4. UPDATE DynamoDB: append [VERIFIED BY AGENT] {answer} to session history
  5. DELETE from SQS (receipt handle)

--- POLLING MECHANISM (chat.html → /queue-status) ---
After escalation, frontend polls every 5s for 5 minutes (60 attempts max).
Per-query tracking: each escalated query has its own {query, pollCount, resolved} object.
API: GET /queue-status/{session_id}?query={encoded_query}
Priority 1: Match session_id + query (original requester)
Priority 2: Match query only across ALL sessions (cross-user knowledge sharing)
When found → shows green "Human agent answered: ..." message in chat

--- API ENDPOINTS (main.py) ---
POST /query          — rate 20/min — main chat endpoint
POST /escalate       — rate 5/min  — manual escalation trigger
GET  /queue-status/{session_id}?query= — rate 30/min — polling for human answer
GET  /health         — no limit — health check
GET  /               — no limit — serves chat.html

SECURITY:
- slowapi rate limiting (key: client IP)
- Pydantic field_validator: sanitize_query() on every input (strips null bytes, max 1000 chars)
- detect_prompt_injection(): blocks "ignore instructions", jailbreaks, env var extraction
- mask_pii(): redacts emails, phones, credit cards, SSNs from all log lines
- UUID validation on session_id in /escalate and /queue-status
- SecurityHeadersMiddleware: X-Frame-Options, CSP, HSTS, X-XSS-Protection, nosniff
- Error masking: raw exceptions logged server-side only, generic message to client

--- INGESTION PIPELINE (pipeline.py) ---
Trigger: manual (python -m app.ingestion.pipeline)
Flow: list S3 raw-documents/*.pdf → download to tempfile.mkdtemp() →
      PyPDFLoader → RecursiveCharacterTextSplitter(chunk_size=500, overlap=50) →
      get_bedrock_embedding(chunk) → INSERT into RDS documents table
Embedding target: chunk content (for general retrieval)
Human verified: embed query only (for semantic matching at query time)

--- INTERVIEW Q&A ---
Q: Why LangGraph not LangChain agent?
A: Deterministic state machine — enforces retry logic and escalation paths reliably in production.

Q: Why Groq not OpenAI?
A: Sub-200ms inference — critical for real-time chat. LLaMA 3.1 is open source.

Q: Why pgvector not Pinecone/Weaviate?
A: Unified relational+vector in single AWS service (RDS). Reduces infra complexity.

Q: How does cross-user sharing work?
A: Human answer → embed query only → store with source:human_verified → every user's
   retrieval_node checks this pool FIRST before general docs → semantic match finds paraphrased queries.

Q: What happens if human doesn't answer?
A: Polling times out after 5 minutes (60 polls × 5s). User sees timeout message.

Q: How is chat memory maintained?
A: DynamoDB stores [{query, answer, timestamp}] per session_id. Last 4 turns injected into LLM prompt.

Q: Security risks and mitigations?
A: Rate limiting (slowapi), prompt injection detection, PII masking in logs, UUID validation,
   error masking, CSP headers, XSS sanitization (html.escape in dashboard), SSM for secrets.
